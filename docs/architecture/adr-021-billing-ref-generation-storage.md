# ADR-021 — How `billing_ref` (the account id) is generated and stored

**Status:** Proposed (2026-07-09) · D5 amended and open question 1 resolved (2026-07-13) · D6 added (2026-07-13) · D6 partly superseded (2026-07-14)
**Amendment (2026-08-18):** The one denial reason this ADR wrote for both refusals became two.
`DENIAL_REASON_BILLING_REF_INACTIVE` no longer exists: an agent with no `billing_ref` is denied
`DENIAL_REASON_ACCOUNT_NOT_REGISTERED`, whose remedy is to call `Register`, and an account the SoR
reports as switched off is denied `DENIAL_REASON_ACCOUNT_INACTIVE`, where the agent can only wait.
The two cases had one wire value and therefore one remedy, which was wrong for whichever agent read
it. Both decisions below name the value that now applies.
**Realisation (2026-07-29):** Shipped. `billing_ref` generation and storage live in the Exchange service — `src/exchange/internal/service/register.go` (mint plus the already-assigned fast path), `agent_resolution.go` and `exchange_helpers.go` (resolving the paying account on the charge path). The status above is deliberately unchanged: the decisions below have not been re-reviewed since the last amendment, so read them as the design the shipped code follows, not as a ratified contract.
**Builds on:** ADR-009 (identity boundary), ADR-017 (Agent Identity & Registration — D3, D6, D10).
**Refines:** ADR-017 D6 and D10 — it fills in details those decisions left open.

---

## Context

An agent first becomes known to an Exchange just by sending a signed request: the Exchange saves its
identity — its **subdomain** and public key — in the `ramp.agents` table. That identity alone is enough
for free crawling.

To buy **paid** content the agent must **register**. Registration is when the Exchange creates the
agent's **account**: a record in the SoR and a money account in the ledger (TigerBeetle). `billing_ref`
is the id of that account. It is not the same thing as the identity row in `ramp.agents` — although, as
D3 explains, we store `billing_ref` on that row.

> **SoR** (System of Record) is the store that holds agent accounts and is the single source of truth
> for whether an account is active. It is reached through a small interface (`SoRAdapter`) so its
> backend can change — a plain database now, a CRM such as HubSpot later — without changing the rest.
> ADR-017 D10 introduced it (as the `SoRAdapter`); the term itself comes from the project's GitLab wiki.

ADR-017 already decided what `billing_ref` is *for*:

- there is one per Exchange (D3);
- the Exchange finds the account by the agent's **subdomain**, which it trusts because it has checked
  the request signature — never from anything the caller sends (D6);
- the account is reached through the `SoRAdapter` (D10).

Three practical points were never settled, and the earlier notes did not fully agree on them:

1. What `billing_ref` looks like and how it is generated.
2. Which part of the system generates it.
3. Where the **subdomain → `billing_ref`** link is kept, and how it is looked up on each request.

Some rules already fixed and kept here: `billing_ref` means nothing on its own, there is one per
Exchange, the agent never has to send it, it is not a password, and the account is always found by
subdomain (from the checked signature). `billing_ref` ties three things together: the agent's row in
`ramp.agents`, the account record in the SoR, and the money account in the ledger.

This ADR settles the three open points.

---

## Decision

### D1 — `billing_ref` is a random UUID that RAMP generates

`billing_ref` is a random UUID generated by RAMP. It is not built from the subdomain, and it is not an
id taken from another system. A random id is good for two reasons: no one can guess it (so it stays safe
even if some future code accidentally accepts it as input), and RAMP does not depend on anything outside
itself to generate it.

`billing_ref` is never an id borrowed from an outside customer database (a CRM such as HubSpot). If the
SoR is a CRM, it keeps RAMP's UUID as one of its own fields; the CRM's own internal id is never used as
`billing_ref`.

**Other options we looked at, and why we did not pick them:**

- **Build the id from the subdomain, for example `hash(exchange_id, subdomain)`.** Tempting, because a
  repeat register would then give the same id for free. Turned down: the inputs are public, so anyone
  could work out any agent's id — only safe if the id is *never* accepted as input, a rule a growing
  system will break sooner or later. Worse, if a subdomain is ever reused, the same id comes back and
  the new agent would land on the old agent's money account. It also ties the id to the Exchange's name
  never changing. Not worth it, since we already get safe repeats cheaply (D4).
- **The same idea but with a secret (`HMAC`).** Keeps the "same input, same id" behaviour and also
  cannot be guessed, but it needs a secret that can never change (changing it would change every id).
  The reuse problem stays. Not worth a permanent secret when a UUID has neither problem.
- **Use the CRM's own id as `billing_ref`.** This would make the id the single link to the CRM, but it
  ties an important RAMP id to an outside system's id rules and lifetime (records being merged,
  re-created, or reused). We keep the id ours; a CRM SoR keeps our UUID as a field.
- **Let the SoR generate the id and return it.** A real upside — the id is generated and saved in one
  step. Not chosen: the Slack discussion and ADR-017 D10 have the Exchange passing the id in, and D4's
  "return the id that ends up being used" gives the same safety while keeping the id owned by the
  Exchange.
- **A separate "subdomain → `billing_ref`" table.** Tidier on paper, but it adds a query on every
  request for what is really one more field on a row the Exchange already reads (see D3).

### D2 — The Exchange generates `billing_ref`; the SoR just receives it

The Exchange generates `billing_ref` and passes it to the SoR: `SoRAdapter.OnRegister(billing_ref,
registration_data)` takes it as an input.

The Exchange generates the id with a small, replaceable piece of code (in real use it returns a new
UUID; in tests it can return a fixed value). This code is **not** part of the billing/ledger adapter,
because `billing_ref` is an account id, and the ledger only *uses* it — it does not generate it. The
Exchange gives the same new id to both the SoR (`OnRegister`) and the ledger (`EnsureAccount`).

### D3 — Kept as a new optional column on `ramp.agents`, read on the request the Exchange already makes

The subdomain → `billing_ref` link is kept in the Exchange's own database, as a new **optional
`billing_ref` column on the `ramp.agents` table** — the table that already holds the agent's subdomain
and public key. The column is empty until the agent registers; an empty value on a paid request means
"this agent has not registered for paid content yet."

It is **not** a separate table, and it is **not** in the SoR's database. This keeps the SoR simple, as
ADR-017 D10 wanted.

**Why this costs nothing extra:** on every signed request the Exchange already reads the agent's row to
check the signature (one fast lookup by the row's id). If `billing_ref` sits on that same row, the read
the Exchange already does brings it back too — no second query, no extra trip to the database. A
separate table would add a query on every request; keeping it on the same row avoids that. The link
never changes once set, so it is also easy to hold in memory if we ever want to skip even the first
read — but that is a separate improvement, not needed here. (The `active` flag *does* change over time,
so it keeps its own short-lived cache in front of `isActive` — a different thing.)

**Key changes are safe:** the `ramp.agents` row is keyed on the subdomain, not on the key. When an
agent changes its keys, the subdomain stays the same, so the Exchange **updates the same row** — it
just replaces the stored public key — and does not create a new row. Because `billing_ref` sits on that
same row, a key change leaves it untouched and the account keeps working. Two write paths keep this
true and must stay separate: the identity write (used on first contact and on every key change) sets
only the key and never touches `billing_ref`; the Register flow sets `billing_ref` on its own, keyed on
the same subdomain. That way a key change can never wipe the account link. (A brand-new row appears only
for a *different* subdomain — a different agent — which correctly gets its own `billing_ref`.)

### D4 — A repeat register returns the same id; the stored id wins

Registering twice for the same agent must give back the same `billing_ref`, not a new one. The Exchange
first checks `ramp.agents.billing_ref`; if it is already set, it returns that and does nothing else.

To stay correct even if that row is ever lost and rebuilt, `OnRegister` **returns the id that ends up
being used** — the one passed in if the row is new, or the one already stored if a row for that
subdomain already exists — and the Exchange uses the returned value. So if a freshly generated UUID
happens to clash with an existing account, no harm is done.

The subdomain → `billing_ref` link lives in two places: on `ramp.agents` (in the Exchange's database —
the main copy, used for lookups and the repeat-register check) and in the SoR record (as its id).
Because the Exchange holds the main copy, the SoR's own copy of the subdomain is there only so a human
operator can find the row — not for looking accounts up.

### D5 — The billing adapter moves to `billing_ref` right away (amended 2026-07-13)

> Originally this decision said "the ledger keeps working as before" and left the switch as an open
> question. Amended: we update the billing adapter's account arguments now, as part of the same epic.

What changes, and what does not:

- **`Authorize` identifies the paying account by `billing_ref`.** Its request carries `billing_ref`
  instead of the agent id, and its safe-to-repeat key becomes `(billing_ref, IdempotencyKey)`. The
  service finds `billing_ref` on the agent's `ramp.agents` row — the row it already reads for the
  signature check (D3), so this costs no extra query. An agent whose row has no `billing_ref` has not
  registered and cannot buy paid content: the paid item is refused before any money is reserved, with
  the wire reason `DENIAL_REASON_ACCOUNT_NOT_REGISTERED` and a plain message telling the agent to call
  `Register` first (decided 2026-07-13). Free content is not affected — the free path never talks to
  billing.
- **The id of a pending hold now includes the account.** The ledger builds a hold's id from
  `billing_ref` plus the caller's idempotency key (plus a retry counter). Before, the id used the key
  alone, so two different agents reusing the same key could land on one shared hold. Including the
  account closes that gap; a shared conformance test pins the behaviour on both ledger backends.
- **Old balances are not moved.** Accounts keyed by the agent id existed only in dev and demo setups —
  there is no production ledger yet — so those ledgers are simply recreated. No migration tool is
  built (decided 2026-07-13).
- **`GetBalance` and `GetQuota` take `billing_ref`** instead of the agent id. Nothing calls them in
  production yet, so this is a signature change plus tests.
- **`Record`, `Release` and `Refund` do not change.** They are keyed by `billingID` — the id of one
  reservation, which `Authorize` returns — plus an idempotency key, and they never carry the account
  id. Careful with the similar names: `billingID` means one reservation; `billing_ref` means one
  account.
- **The ledger's hashing stays.** TigerBeetle still turns the `billing_ref` text into its own account
  number (the existing `AccountID(prefix, ns + billing_ref)` step). `billing_ref` stays plain text;
  the ledger stores no text.

### D6 — The Broker's cost guard keys on the agent identity, not `Requester.billing_ref` (added 2026-07-13)

> This decision is about the **Broker**, not the Exchange account handle the rest of
> this ADR describes — but it belongs here because it settles how `Requester.billing_ref` may and may not
> be used, which is the trust model this ADR owns.

There are two different things that were both once called `billing_ref`:

- the **account handle** — the id this ADR is about, minted by the Exchange from the verified signature,
  stored on `ramp.agents`, authoritative;
- **`Requester.billing_ref`** — a free-text label the *caller* writes into a request (a rename was proposed for it
  to `billing_label` to make the difference visible). Nobody authenticates it.

The Broker's cost guard (the resolve/discovery budget check) used to key on that **caller-written label**.
Because the label is unauthenticated, an over-budget agent could evade the guard by leaving it blank
(the guard skipped the check) or by writing a different value. That is exactly the trust-confusion this
ADR's two-names distinction warns about: an unverified value driving a money decision.

Decision: **the Broker's cost guard keys on the authenticated agent identity** (`Requester.id`, which the
Broker's httpsig middleware has already verified via `authorizeAgentSelfAct` — the signed `Signature-Agent`
must equal `requester.id`), and it accumulates **per agent, per period**. `Requester.billing_ref` is
**attribution-only**: the Broker still echoes it to the Exchange for the customer's own usage reports, but
nothing on the guard path reads it. The guard's *limit* stays caller-supplied (a guardrail, not a
third-party guarantee): the agent declares its own ceiling, which is the whole point of a self-guard, so
no server-side per-agent limit is planned.

Note on "double-billing": the Broker recording spend here is **not** the double-count that earlier notes
warned about. That warning was about the retired broker-authored-execute path. The Broker no longer
executes or bills — the Exchange is the sole biller — so the Broker's per-agent counter is a separate,
discovery-side guard on *brokered offer value*, distinct from the Exchange's `transaction_log`.

**Superseded in part (2026-07-14).** D6 above left `Requester.billing_ref` on the wire as an
"attribution-only" label the Broker echoes to the Exchange. In practice no Exchange code ever read that
field, so the attribution role was aspirational, not load-bearing. The protocol therefore **drops
`Requester.billing_ref` entirely** (reserving field 5 and the name), superseding the proposed rename. Nothing is lost: the cost guard already keys on the authenticated identity (D6),
and the account handle this ADR governs (`RegisterResponse.billing_ref`) is a different message and is
unaffected. The only standing claim this reverses is D6's "the Broker still echoes it to the Exchange" —
there is no longer a field to echo.

## Consequences

### Good
- One clear answer for how `billing_ref` is generated, who generates it, and where it is kept.
- Reading `billing_ref` on each request costs nothing beyond the row read the Exchange already does (D3).
- The id is fully owned by RAMP and cannot be guessed; it does not depend on any outside system.
- The SoR stays simple, as ADR-017 D10 intended; the Exchange holds the main copy of the link.

### Costs
- The subdomain → `billing_ref` link is stored in two places (the Exchange's database and the SoR
  record). D4 names the Exchange copy the main one and keeps them in step, but it is still something to
  keep consistent.
- Adds one optional column and a small database change to `ramp.agents`, plus the small id-generating
  helper.

## Follow-up

- The agent-registration work should follow this ADR and point to it for how `billing_ref` is generated,
  stored, and looked up.
- ADR-017 D10 can get a short extra line pointing here; nothing in D10 is rewritten.
- **Checking the account's active flag on each paid transaction** — split out into its
  own ticket on 2026-07-13, now implemented. Each paid item reads the SoR-owned active flag before
  any money is reserved (through the 30-second read-through cache built for exactly this) and a
  switched-off account is denied in-body with `DENIAL_REASON_ACCOUNT_INACTIVE`. Error policy on
  the hot path: **definitive answers fail closed** — a known-inactive account and an account the SoR
  does not know are both denied; **transient SoR read errors fail open** — the transaction proceeds
  with a warning log. Reasons: the ledger balance check still bounds what any account can spend, a
  SoR outage must not stop every paid transaction on the platform, and the cache never stores
  errors, so enforcement resumes the moment the SoR answers again. Free content is untouched (it
  never reaches billing).
